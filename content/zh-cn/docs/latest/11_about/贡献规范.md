欢迎提交问题、修复与文档改进。先说明使用的分支、提交、Java 版本、复现步骤及预期结果；示例日志请移除凭据与个人信息。

## 提交修改

从目标维护分支创建工作分支，修改关联模块及 README，运行最小相关验证，再提交 Pull Request。业务项目接入无需执行下列框架源码贡献检查。

## 构建与测试

项目要求 JDK 17，并使用 Maven 构建。日常开发建议从目标模块开始验证：

```bash
# 运行目标模块及其依赖的单元测试
mvn -pl macula-boot-starters/macula-boot-starter-web -am test

# 运行全仓库单元测试
mvn test

# 运行单元测试、集成测试并完成构建验证
mvn verify
```

### 测试分层规范

项目通过 Maven Surefire 和 Failsafe 区分两类测试：

| 类型 | 命名 | 使用场景 | 执行命令 |
| --- | --- | --- | --- |
| 单元测试 | `*Test`、`*Tests`、`Test*`、`*TestCase` | 纯逻辑、Mockito，以及使用 `ApplicationContextRunner` / `WebApplicationContextRunner` 的轻量自动配置测试 | `mvn test` |
| 集成测试 | `*IT`、`IT*`、`*ITCase` | `@SpringBootTest` 完整上下文、自动配置发现，以及 Redis、数据库、消息队列等基础设施协作 | `mvn verify` |

编写测试时遵循以下约定：

- 纯业务逻辑优先使用普通 JUnit 和 Mockito，不启动 Spring。
- Starter 的条件装配、属性绑定和 Bean 回退优先使用 Context Runner。
- `@SpringBootTest` 仅用于需要完整应用上下文的集成测试，并采用 `*IT` 命名。
- 依赖 Redis、数据库、Kafka、RocketMQ 等外部服务的测试必须归入集成测试，并明确运行条件。
- 测试应可重复、与执行顺序无关，不依赖随机值或未声明的共享状态。

测试报告分别生成在：

```text
target/surefire-reports    # 单元测试
target/failsafe-reports    # 集成测试
```

当前 CI 会提供 Redis 7 并执行 `mvn verify`。Kafka、RocketMQ 和 TinyID 的真实服务测试在基础设施未提供时带有明确的禁用原因，同时各模块保留不连接外部服务的自动配置测试。

### 发布构建

项目使用 `${revision}` 管理版本。生成用于发布的完整构建产物时需要启用 `deploy` Profile：

```bash
mvn clean install -DskipTests=true -Dgpg.skip=true -Pdeploy
```

`deploy` Profile 默认跳过测试，因此发布前应先执行 `mvn verify`。`release.sh` 会涉及分支、提交、标签和远端推送，仅应在确认版本和工作区状态后使用。

## 代码风格与格式化

Macula Boot 的格式化规则已经随仓库提交，使用 IntelliJ IDEA **内置 Formatter**，无需另外安装或导入一套阿里 Formatter。阿里规范提供通用工程原则，实际排版以当前分支的项目规则为准，避免个人全局方案覆盖项目设置。

### 规则文件

| 文件 | 用途 |
| --- | --- |
| `.idea/codeStyles/codeStyleConfig.xml` | 启用项目级 Code Style，使用随仓库维护的方案 |
| `.idea/codeStyles/Project.xml` | IDEA 的 Java 换行、import、Javadoc 和 Formatter 标记设置 |
| `.editorconfig` | 字符编码、行尾、缩进及 Java 行宽等基础规则 |
| `.config/license-header` | 新增 Java 文件的 Apache License 2.0 版权头模板 |
| `.config/checkstyle.xml` / `checkstyle-header.txt` | 静态风格检查及版权头匹配规则 |

这些规则随目标分支维护，不从其他项目复制全局格式方案，也不把 IDEA XML 当作所有编辑器通用的导入格式。

### 内置 Formatter 使用

1. 从仓库根目录打开项目，保留版本化的 `.idea/codeStyles`，确认 `Editor | Code Style` 使用项目方案并启用 EditorConfig 支持。
2. 对本次修改的文件执行 `Code | Reformat Code`，并按需执行 Optimize Imports，检查导入和换行结果。
3. 可在 `Tools | Actions on Save` 启用 Reformat code，优先选择变更行或限定变更文件；提交前检查差异，避免格式化整个历史仓库。
4. 若结果不一致，检查个人全局方案、自动缩进检测和其他格式化插件是否覆盖项目配置，再核对当前分支的规则文件。

其他编辑器使用 `.editorconfig` 对齐基础规则，并核对 Java import 与换行风格。IDEA 内置 Formatter 的操作方式可参考 [JetBrains 文档](https://www.jetbrains.com/help/idea/reformat-and-rearrange-code.html)。

### 当前排版约定

| 项目 | 仓库设置 |
| --- | --- |
| 编码与行尾 | UTF-8、LF，文件末尾保留换行 |
| Java 缩进 | 4 个空格，续行缩进 8 个空格，不使用 Tab |
| Java 行宽 | 120；长参数、调用链和表达式按项目规则换行 |
| import | 避免自动合并成通配导入，清理冗余和未使用项 |
| import 分组 | `java`、`javax`，其他包，静态导入；组间按项目方案分隔 |
| Javadoc | 不为了视觉对齐填充大量空格，不保留无内容的参数、返回和异常标签 |
| Formatter 标记 | 支持 `@formatter:off` / `@formatter:on`，仅用于确有必要保留布局的局部片段 |

EditorConfig 与项目方案共同决定排版，未定义的细节由当前编辑器格式器处理。不要通过大范围 Formatter 关闭标记规避风格要求。

### Formatter 与 Checkstyle 分工

Formatter 修改源码布局；Checkstyle 检查规则并报告问题，不修改文件。两者不能互相替代，也都不能证明业务逻辑正确。

当前 `.github/workflows/verification.yml` 检查相对比较基线变更的 Java 文件，覆盖版权头、类型 Javadoc、导入和基础代码结构等规则；普通 Maven 构建不自动重排源码。需要本地检查全仓时，在 Boot 根目录运行：

```bash
mvn -N checkstyle:check
```

全仓审计可能包含存量问题，应区分本次引入与已有告警；不能把“仅变更文件通过”说成全仓已清零。当前规则不承担完整的缩进、换行和行宽排版检查，这部分交由编辑器 Formatter。

新增 Java 文件使用仓库版权头，类型注释按下节补齐。完成格式化和静态检查后，仍需运行目标模块的单元测试及适用的集成验证。

## 开发约定

- Java 代码保持 JDK 17 兼容，包名沿用 `dev.macula...`。
- 依赖版本统一在 [`macula-boot-parent/pom.xml`](https://github.com/macula-projects/macula-boot/blob/3fbd28dc74d683055d27b81929971c0e45047878/macula-boot-parent/pom.xml) 管理，避免在子模块重复声明。
- Starter 自动配置应可禁用、可覆盖，并使用 `@ConditionalOnMissingBean` 等机制为业务项目保留扩展能力。
- 新增或移动自动配置时，同步维护 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`。
- 公共 API、配置键或行为发生变化时，同步更新模块 README 和测试。

Java 注释遵循以下约定：

- 类、接口、枚举、注解、Record 及测试类必须使用类级 Javadoc 说明职责，内部辅助类型也不能只写普通行注释。
- 顶层类型的 Javadoc 必须包含非空的 `@author`、`@since`；内部类型无需重复 `@author`，但仍须包含 `@since`，格式参考 `AsyncAutoConfiguration`。
- 对外公开的类和方法应说明用途、参数、返回值、异常及重要约束；实现显而易见时不写逐行翻译代码的注释。
- `TODO` 应说明待办事项和上下文，避免无意义的占位注释；修改行为时同步更新关联注释。

更多路线规划参见 [Roadmap](https://github.com/macula-projects/macula-boot/blob/3fbd28dc74d683055d27b81929971c0e45047878/Roadmap.md)。


## 文档贡献

网站使用 `npm ci` 和 `npm run build` 构建。latest 对应 Boot main，历史版本按各自分支维护；组件保留统一六段结构，来源路径和提交写入 Front Matter。人工维护页面标记 `manual_content: true`，同步前在临时副本比较。

提交 PR 时说明改了什么、验证范围及限制；源代码单测、集成测试、真实外部服务联调与文档静态构建分别报告。
