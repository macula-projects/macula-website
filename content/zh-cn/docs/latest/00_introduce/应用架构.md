Macula 将平台公共能力与业务应用分开组织。Macula Cloud 管理统一身份、应用和权限；业务应用使用 Macula Boot 的组件实现自己的接口、规则与数据。下面以一个管理端应用说明协作关系。

## 平台与业务

{{< application-architecture >}}

实线表示业务请求，虚线表示认证、权限或平台能力连接。图中的应用 Gateway 与 Cloud Gateway 是不同的入口：前者接收业务请求，后者向业务应用提供 Cloud 服务。

Cloud 管理端用于平台管理，业务管理端用于本应用的业务操作。二者可使用统一身份体系，但有各自的页面、菜单归属与接口。

## 模块职责

| 模块 | 职责 | 扩展边界 |
| --- | --- | --- |
| 前端 | 页面、交互和业务请求 | 通过业务入口访问后端 |
| Gateway | HTTP/WebSocket 路由、入口认证授权、JWT 转换及接口保护 | 按入口需求配置，不承担核心业务事务 |
| BFF | 面向页面聚合接口，获取平台用户与菜单 | 编排业务服务，组织适合页面的返回结果 |
| Service | 业务规则、事务和数据访问 | 维护自身数据，通过 API 契约开放能力 |
| API | Feign 接口、请求与返回模型、错误约定 | 是编译依赖的契约制品，不单独启动 |
| Parent | 统一依赖、插件和构建约定 | 是构建模块，不单独启动 |

需要时还可采用 Basic 封装公共业务服务、OpenAPI 组织对外接口、Thirdparty 隔离第三方协议。Samples 提供这些边界的参考骨架，具体业务由应用实现；简单项目按需求选择部署模块。

## 一次业务请求

以“查询应用列表”为例：

1. 用户通过 IAM 完成登录，业务前端取得外部访问令牌。
2. 前端携带令牌请求应用 Gateway，网关完成入口认证及相应访问控制，转发时使用内部 JWT。
3. BFF 验证 JWT，按业务方法的授权要求检查权限，并通过 API 契约调用业务 Service。
4. Service 验证调用身份，执行查询规则，经 Mapper 访问自身数据库，将结果转换为接口返回模型。
5. BFF 按页面需要组织结果，经过 Gateway 返回前端。

新增、修改等操作仍沿用这条链路，事务与核心业务状态变更由相应 Service 负责。身份、方法权限和资源归属的细节见[安全架构](/docs/latest/00_introduce/安全架构/)；查询条件和返回对象怎样转换见[应用分层](/docs/latest/00_introduce/值对象与分层/)。

## 平台连接

| 连接方向 | 用途 |
| --- | --- |
| 应用 Gateway → Cloud IAM | 验证外部 Token |
| BFF → Cloud Gateway → System | 获取应用对应的用户、菜单与操作权限 |
| BFF / Service → 应用 Gateway 的 JWK | 获取公钥，验证内部 JWT |
| 应用 Gateway → Cloud System Redis | 读取平台权限与应用凭据信息 |

这些方向不能仅凭“网关地址”互换。具体配置键在安全架构中概要说明，实际地址、登记字段与验收步骤见[首次接入](/docs/latest/04_devmanual/首次接入macula-cloud/)。

## 配套能力

注册与配置中心负责服务定位和环境配置；数据库与 Redis 按各应用职责部署和使用。可观测性关联入口、远程调用和业务日志，帮助定位跨服务问题；业务审计与操作日志负责记录操作事实，两者用途不同。

具体组件查阅[平台能力](/docs/latest/01_services/)，实际模块、端口与配置查阅[示例模块说明](/docs/latest/04_devmanual/模块说明/)。本章的架构关系同样适用于按需组合的业务项目，不要求照搬 Samples 的全部模块。
