业务功能写好后，先用单元测试检查规则，再用集成测试检查真实协作。本章介绍两类测试的编写与执行机理；应用启动、前后端联调和整条请求链路的验证见[运行与测试](/docs/latest/04_devmanual/运行与测试/)。

以下约定以当前 Macula Boot Parent 为准。代码中的业务小例子和 Redis 测试是**新增测试的教学示例**，不是 Samples 仓库已经提供的测试文件。

## 测试分层

| 类型 | 验证对象 | 推荐方式 | 命名与执行 |
| --- | --- | --- | --- |
| 单元测试 | 参数边界、业务分支、转换、异常与协作调用 | JUnit Jupiter、Mockito，不启动 Spring、不连接外部服务 | `*Test`；`mvn test` |
| 自动配置测试 | 条件装配、属性绑定、用户 Bean 回退 | `ApplicationContextRunner`，只加载所需配置 | `*Test`；`mvn test` |
| 集成测试 | Spring Bean 协作、代理、完整装配，或真实数据库、Redis、消息队列 | `@SpringBootTest` 或明确连接真实依赖的测试 | `*IT`；`mvn verify` |

- 纯逻辑测试直接创建对象；不要为每个测试都加 `@SpringBootTest`。
- Context Runner 虽然创建小型 Spring 容器，本项目将这类隔离的配置测试归在单元测试中。
- 使用完整应用上下文或连接真实外部服务时，归入集成测试，即使测试方法很短。
- Maven 按**类名与插件配置**选择测试，不会根据是否存在 `@SpringBootTest` 自动分类。命名不正确会导致执行阶段错误或漏测。

## 依赖与目录

Samples 的 `macula-samples-parent` 已继承 Macula Boot Parent，并声明测试依赖，业务子模块通常无需重复添加。自建项目尚未引入时，在目标模块的 `pom.xml` 声明：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>
```

JUnit Jupiter、Mockito、AssertJ 和 Spring Test 随测试 Starter 提供，版本交给 Parent 管理。测试代码和资源采用 Maven 标准目录：

```text
macula-samples-service1/
├── src/main/java/                 # 被测业务代码
├── src/test/java/                 # 单元与集成测试均放在这里
│   └── dev/macula/samples/service1/
│       ├── service/OrderTitleServiceTest.java
│       └── redis/RedisAccessIT.java
└── src/test/resources/
    └── application-test.yml       # 测试专用配置
```

默认没有独立的 `src/it/java`。新增测试类后检查实际执行数量；只有 `main` 方法的诊断程序不是 JUnit 用例。

## 编写单元测试

以“按编号读取订单标题”为例。先在业务包中定义协作边界，下面两个类型分别放在同名 Java 文件中，均使用 `dev.macula.samples.service1.service` 包：

```java
package dev.macula.samples.service1.service;

import java.util.Optional;

/** 读取订单标题的数据访问边界。 */
public interface OrderTitleRepository {
    Optional<String> findTitle(long orderId);
}
```

```java
package dev.macula.samples.service1.service;

import java.util.NoSuchElementException;

/** 校验订单编号并读取标题。 */
public class OrderTitleService {
    private final OrderTitleRepository repository;

    public OrderTitleService(OrderTitleRepository repository) {
        this.repository = repository;
    }

    public String getTitle(long orderId) {
        if (orderId <= 0) {
            throw new IllegalArgumentException("订单编号必须大于零");
        }
        return repository.findTitle(orderId)
            .orElseThrow(() -> new NoSuchElementException("订单不存在"));
    }
}
```

`OrderTitleServiceTest.java` 用 Mock 替代数据访问，只验证这层业务规则：

```java
package dev.macula.samples.service1.service;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.verifyNoInteractions;
import static org.mockito.Mockito.when;

import java.util.NoSuchElementException;
import java.util.Optional;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

/** 订单标题查询的成功、缺失与非法输入测试。 */
@ExtendWith(MockitoExtension.class)
class OrderTitleServiceTest {
    @Mock
    private OrderTitleRepository repository;

    @InjectMocks
    private OrderTitleService service;

    @Test
    void returnsTitleWhenOrderExists() {
        when(repository.findTitle(1001L)).thenReturn(Optional.of("采购订单"));

        assertEquals("采购订单", service.getTitle(1001L));
        verify(repository).findTitle(1001L);
    }

    @Test
    void rejectsInvalidIdBeforeReadingRepository() {
        assertThrows(IllegalArgumentException.class, () -> service.getTitle(0L));
        verifyNoInteractions(repository);
    }

    @Test
    void rejectsMissingOrder() {
        when(repository.findTitle(1002L)).thenReturn(Optional.empty());

        assertThrows(NoSuchElementException.class, () -> service.getTitle(1002L));
    }
}
```

一次用例分三步：准备输入和协作返回值 → 调用被测方法 → 断言结果、异常或关键副作用。`MockitoExtension` 在每个用例执行前初始化 Mock，`@InjectMocks` 将它交给被测对象；整个过程不启动 Spring，也不访问数据库。

这个测试能证明非法编号在数据访问前被拒绝，不能证明真实 SQL、事务或权限注解生效。直接创建的对象没有经过 Spring 代理，`@Transactional`、`@PreAuthorize` 等行为需要通过容器中的 Bean 另做集成验证。示例省略版权头等工程排版要求，提交框架测试时仍遵守[贡献规范](/docs/latest/11_about/贡献规范/)。

## 编写集成测试

### 明确测试边界

集成测试只加载本次需要协作的组件，先明确：

1. 测试 Spring 装配、真实 Redis，还是完整 Service1 应用？
2. 外部服务的地址、账号和测试数据由谁准备？
3. 测试失败后如何清理本次数据，避免影响其他用例？

下面验证“通过 Spring 注入的模板读写真实 Redis”。Service1 已依赖 Redis Starter，无需额外声明 Redis 客户端。使用独立测试配置和显式 Bean，避免为了检查 Redis 而启动 Nacos、MySQL、IAM 等整套环境。

### 集中测试配置

新增 `src/test/resources/application-test.yml`：

```yaml
spring:
  application:
    name: macula-samples-redis-test
  data:
    redis:
      host: ${TEST_REDIS_HOST:127.0.0.1}
      port: ${TEST_REDIS_PORT}
      database: ${TEST_REDIS_DATABASE:15}
      password: ${TEST_REDIS_PASSWORD:}
```

| 配置 | 用途 |
| --- | --- |
| `TEST_REDIS_PORT` | 必填，明确指定独立测试 Redis，避免误连默认端口 |
| `TEST_REDIS_DATABASE` | 测试逻辑库，默认 15；适用于支持逻辑库的单机 Redis，不代表物理隔离 |
| `TEST_REDIS_PASSWORD` | 从运行环境注入，不将真实密码写入仓库 |

此例在注解中指定 `spring.config.location`，**替换默认配置文件搜索位置**，只读取这份测试配置；不是用测试 profile 叠加完整业务配置。普通应用测试使用 `@ActiveProfiles("test")` 时，仍会加载基础 `application.yml`，其中的 Nacos 导入不会仅因切换 profile 自动消失。

### 编写真实读写用例

新增 `src/test/java/dev/macula/samples/service1/redis/RedisAccessIT.java`：

```java
package dev.macula.samples.service1.redis;

import static org.junit.jupiter.api.Assertions.assertEquals;

import java.time.Duration;
import java.util.UUID;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.connection.RedisStandaloneConfiguration;
import org.springframework.data.redis.connection.lettuce.LettuceConnectionFactory;
import org.springframework.data.redis.core.StringRedisTemplate;

/** Spring 模板与真实 Redis 的读写集成测试。 */
@SpringBootTest(
    classes = RedisAccessIT.RedisTestConfiguration.class,
    webEnvironment = SpringBootTest.WebEnvironment.NONE,
    properties = "spring.config.location=classpath:/application-test.yml"
)
class RedisAccessIT {
    @Autowired
    private StringRedisTemplate redis;

    private final String key = "macula-test:" + UUID.randomUUID();

    @Test
    void readsBackWrittenValue() {
        redis.opsForValue().set(key, "ready", Duration.ofSeconds(30));

        assertEquals("ready", redis.opsForValue().get(key));
    }

    @AfterEach
    void cleanUp() {
        redis.delete(key);
    }

    /** 仅装配本用例需要的 Redis 连接与模板。 */
    @Configuration(proxyBeanMethods = false)
    static class RedisTestConfiguration {
        @Bean
        LettuceConnectionFactory connectionFactory(
                @Value("${spring.data.redis.host}") String host,
                @Value("${spring.data.redis.port}") int port,
                @Value("${spring.data.redis.database}") int database,
                @Value("${spring.data.redis.password:}") String password) {
            RedisStandaloneConfiguration config =
                new RedisStandaloneConfiguration(host, port);
            config.setDatabase(database);
            if (!password.isEmpty()) {
                config.setPassword(password);
            }
            return new LettuceConnectionFactory(config);
        }

        @Bean
        StringRedisTemplate redisTemplate(LettuceConnectionFactory factory) {
            return new StringRedisTemplate(factory);
        }
    }
}
```

- Spring 创建连接工厂和模板，再注入测试类；断言使用真实 Redis 的返回值，不预设 Mock 结果。
- 唯一 Key 避免不同用例相互覆盖；删除本次 Key，过期时间作为异常退出时的兜底。不要对共享 Redis 执行 `FLUSHDB`。
- 此例验证模板与真实连接，**没有验证 Macula Redis 自动配置发现或完整应用启动**。检查后两者时，要加载真实自动配置或应用入口，并准备其全部依赖。
- 没有 Redis、端口错误或认证失败时，用例应失败并报告环境问题；不能捕获异常后只打印日志，或改成无条件通过。

数据库测试同样准备独立 schema、迁移和最小数据。测试线程内的 Spring 测试事务通常可回滚；经真实 HTTP 请求触发的服务端事务、异步任务、Redis 和消息发送不会随测试方法事务自动回滚，必须安排独立清理。容器化依赖可按项目需要使用 Testcontainers，并明确 Docker 条件和生命周期。

## 测试运行机理

### Maven 如何选择测试

```text
编译主代码与测试代码
        ↓
 test：Surefire → 命名匹配的单元测试
        ↓
 package：生成制品
        ↓
 pre-integration-test：准备环境（需要自行绑定插件或由测试准备）
        ↓
 integration-test：Failsafe → 命名匹配的集成测试，记录结果
        ↓
 post-integration-test：清理环境（需要自行配置）
        ↓
 verify：Failsafe 检查集成测试结果，决定构建是否通过
```

1. Parent 的 Surefire 包含 `Test*`、`*Test`、`*Tests`、`*TestCase`，并排除 `IT*`、`*IT`、`*ITCase`。
2. Failsafe 包含 `IT*`、`*IT`、`*ITCase`，绑定 `integration-test` 和 `verify` 两个目标。
3. 插件把选中的测试交给 JUnit Platform，Jupiter 引擎执行 `@Test` 及前后置回调，断言失败或未处理异常反馈给插件。
4. `mvn test` 到 `test` 阶段结束；`mvn verify` 会先运行单元测试，再运行集成测试。两类源文件都在 `test-compile` 阶段编译，因此集成测试代码编译错误也会使 `mvn test` 失败。
5. Failsafe 将正常用例失败的构建判定延后到 `verify`，让已配置的后置清理阶段有机会执行；不代表任意构建故障都能保证清理。执行到 `verify`，不要只运行 `mvn integration-test`。

Parent 不会自动启动 Redis、数据库或 Macula Cloud。IDE 直接运行类通常也不经过上述 Maven 阶段，IDE 中通过后仍需用 Maven 检查命名、插件和环境是否一致。

### Spring 如何参与

| 方式 | 执行过程与边界 |
| --- | --- |
| 普通 JUnit / Mockito | JUnit 执行生命周期回调和测试方法，Mockito 提供受控协作对象；没有 Spring 容器 |
| Context Runner | 每次 `run` 创建所需的小型上下文，应用属性和用户配置后断言 Bean，结束时关闭上下文 |
| `@SpringBootTest` | 通过 Spring TestContext 与 SpringApplication 创建上下文，注入 Bean 后执行用例；相同配置的上下文可在同一测试进程中复用 |

`@SpringBootTest` 默认不启动真实 HTTP 服务器；`NONE` 不创建 Web 环境，`RANDOM_PORT` 才启动监听随机端口的服务器。上下文缓存不会替你清理数据库、缓存和 Bean 的可变状态；用例须独立，不能依赖执行顺序。

## Starter 二次开发

修改 Starter 时，先用 Context Runner 检查默认装配、开关关闭、条件不满足和用户 Bean 覆盖。下面是 Async 已提交测试中的源码节选：

```java
private final ApplicationContextRunner contextRunner = new ApplicationContextRunner()
    .withConfiguration(AutoConfigurations.of(AsyncAutoConfiguration.class));
```

这里显式传入了自动配置类，能验证类内的装配逻辑，不能证明 `AutoConfiguration.imports` 已正确登记。增加少量按正常发现链路启动的 `*IT` 补足这条边界。完整用例见 [AsyncAutoConfigurationTest 源码](https://github.com/macula-projects/macula-boot/blob/5ff9b5c8e6166449ced7512cd3bf74a672aa922e/macula-boot-starters/macula-boot-starter-async/src/test/java/dev/macula/boot/starter/async/config/AsyncAutoConfigurationTest.java)，真实缓存协作可参考 [RedisCacheIT 源码](https://github.com/macula-projects/macula-boot/blob/5ff9b5c8e6166449ced7512cd3bf74a672aa922e/macula-boot-starters/macula-boot-starter-cache/src/test/java/dev/macula/boot/starter/cache/test/RedisCacheIT.java)。

## 运行与定位

在 Samples 单仓根目录执行。先确认所用 Boot Parent 包含上述插件配置；快照可能随本地或远端制品变化，必要时检查目标模块的 `mvn help:effective-pom`。

```bash
# Service1 及所需模块的单元测试
mvn -pl macula-samples-service1 -am test -Plocal

# 指定单个用例；-am 构建的依赖模块可没有同名测试
mvn -pl macula-samples-service1 -am test -Plocal \
  '-Dtest=OrderTitleServiceTest#rejectsInvalidIdBeforeReadingRepository' \
  -Dsurefire.failIfNoSpecifiedTests=false

# 环境准备好后，先设置测试 Redis 端口（按你的实际环境填写）
export TEST_REDIS_PORT=26379

# 先运行单元测试，再执行指定集成测试并检查结果
mvn -pl macula-samples-service1 -am verify -Plocal \
  -Dit.test=RedisAccessIT -Dfailsafe.failIfNoSpecifiedTests=false
```

`-Plocal` 选择 Maven 构建 profile，可能参与业务资源过滤；不等于激活 Spring 的 `test` profile。上面的 Redis 测试通过注解显式选择测试文件。`-Dit.test` 只筛选集成测试，前面的 Surefire 单元测试仍会执行。

| 现象 | 先检查 |
| --- | --- |
| 没有执行用例 | 类名、JUnit 的 `@Test` 导入、目标模块、有效 POM、是否跳过测试；检查测试数量不能只看 BUILD SUCCESS |
| `mvn test` 意外连接外部服务 | 是否把完整上下文 / 外部依赖用例命名为 `*Test` |
| Spring 上下文启动失败 | 找第一个根因，核对测试文件是否仍导入 Nacos、是否加载了不需要的自动配置 |
| Redis / 数据库连接失败 | 实际地址、凭据、端口映射和测试资源；与业务断言失败分开定位 |
| 本地通过、CI 失败 | JDK、Parent 制品、环境变量、基础设施、并行共享数据与 profile 的差别 |

单元报告在各模块 `target/surefire-reports/`，集成报告在 `target/failsafe-reports/`。记录实际命令、测试数量、失败 / 错误 / 跳过数及外部环境；跳过或未运行不能写为验证通过。

关于 Maven 的阶段与结果检查见 [Failsafe 官方说明](https://maven.apache.org/surefire/maven-failsafe-plugin/)；上下文启动方式见 [Spring Boot 测试说明](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html)。
