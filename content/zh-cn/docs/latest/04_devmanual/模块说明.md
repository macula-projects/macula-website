## 模块总览

| 模块 | 职责 | 默认本地端口 |
| --- | --- | ---: |
| Parent | 后端依赖、插件、构建 profile | — |
| API | Basic / Service1 的服务间契约 | — |
| Gateway | 路由、IAM Token 验证、内部 JWT 转换 | 6000 |
| Admin BFF | 管理端接口聚合与 Macula Cloud 接入 | 6001 |
| OpenAPI | 面向外部调用方的接口聚合边界 | 6002 |
| Service1 | 业务实现、数据访问与数据库迁移 | 6003 |
| Basic | 可独立部署的公共服务边界 | 6004 |
| Thirdparty | 对第三方协议和模型的封装边界 | 6005 |
| Admin | Vue 管理端 | 5800 |

端口用于 IDE 本地运行。完整容器模式只对宿主机发布 Gateway 和 Admin，其余后端通过容器网络访问。

## Parent：统一构建

`macula-samples-parent/pom.xml` 维护后端公共依赖、插件及 `local/dev/stg/pet/prd` profile，使用 `profile.active` 将构建环境传给资源配置。模块内按需声明 Starter，公共版本由 Parent / Macula Boot 管理。

Parent 是构建模块，没有 application.yml，也不启动 Web 服务。前端依赖由 Admin 的 package.json 与锁文件管理。

## API：服务间契约

`macula-samples-api` 是聚合 POM，包含 `macula-samples-basic-api`、`macula-samples-service1-api`。

- `api/`：Feign 接口及调用契约。
- `form/`、`query/`：请求表单与查询条件。
- `vo/`、`errors/`：返回模型和服务错误约定。

例如 `ApplicationFeignClient` 的服务名为 `macula-samples-service1`，声明 `/api/v1/app` 等接口。调用方引用 API 制品，不依赖 Service1 的实现包；实体、Mapper 与业务实现留在业务服务中。

API 模块不启动应用，也不配置 JWK 或运行时可观测性导出。

## Gateway：统一入口

`macula-samples-gateway` 使用 Spring Cloud Gateway。当前路由在 `application.yml` 的 `spring.cloud.gateway.server.webflux.routes` 下定义：

| 入口 | 目标 | 路径处理 |
| --- | --- | --- |
| `/admin/**` | `lb://macula-samples-admin-bff` | StripPrefix=1 |
| `/openapi/**` | `lb://macula-samples-openapi` | StripPrefix=1 |

网关通过 IAM 的 introspection 地址验证客户端 Token，再将内部 JWT 传给后端。下游从本应用网关的 `/oauth2/jwks` 获取验证公钥。

Gateway 同时连接项目 Redis 与 Cloud System Redis。当前源码的 `RedisConfiguration` 显式绑定 `spring.redis.*` 和 `spring.redis.system.*`，这是 Samples 网关自定义的配置契约，不能直接改成业务服务的 Redis 前缀。

## Admin BFF：面向管理端的聚合

`macula-samples-admin-bff` 面向 Admin 组织接口，`ApplicationController → ApplicationService → ApplicationFeignClient` 将应用管理请求转给 Service1。

BFF 引入 System Starter，通过 `macula.cloud.endpoint`、`app-key`、`secret-key` 访问 Cloud System，提供用户与菜单能力。`endpoint` 指向 **Macula Cloud Gateway**，不指向 Samples Gateway。

同时，BFF 作为资源服务器配置 **Samples Gateway** 的 `spring.security.oauth2.resourceserver.jwt.jwk-set-uri`。这两个地址服务于不同方向，不能互换。

管理端用户信息的典型路径为：浏览器 `/api/admin/api/v1/users/me` → Vite / Nginx 去掉 `/api` → Gateway 去掉 `/admin` → BFF `/api/v1/users/me`。

BFF 与业务服务还通过 Security Starter 使用 `@PreAuthorize`、`@PostAuthorize`、`@CheckOwner` 做操作与数据级授权。整体分层见[请求链路](/docs/latest/00_introduce/请求链路/)，具体用法见 [Security](/docs/latest/01_services/框架基础/security/)。

## Service1：业务与持久化

`macula-samples-service1` 的已提交主线示例是应用管理：

```text
controller/ApplicationController
service/ApplicationService → service/impl/ApplicationServiceImpl
converter/ApplicationConverter
mapper/ApplicationMapper
pojo/bo/ApplicationBO、pojo/entity/Application
resources/db/migration/V1__baseline.sql
```

Controller 接收请求，Service 组织业务和事务，Mapper 处理数据访问，Converter 负责不同层的对象转换。接口表单、查询和返回模型由 Service1 API 契约模块共享。

该模块使用 MyBatis-Plus、Redis、Flyway 及网关 JWT 校验。新增业务的完整步骤见[创建示例服务](/docs/latest/04_devmanual/创建服务模块/)。

## Basic：公共服务边界

`macula-samples-basic` 是可部署的公共服务模块。当前单仓主线提供启动类和运行配置骨架，具体公共能力按项目需要实现；通用框架能力继续复用 Macula Boot。

需要跨服务复用的接口可放入 Basic API。该模块使用应用网关的 JWK 地址，不承担 IAM 登录或全局系统管理。

## OpenAPI：对外接口边界

`macula-samples-openapi` 用于组织面向外部调用方的 API，Gateway 已预留 `/openapi/**` 路由。当前单仓主线提供运行骨架，业务接口需要按实际需求实现。

接口的数据模型、版本、返回结构与内部业务解耦；调用内部服务时使用其 API 契约。OpenAPI 同样作为资源服务器校验应用网关签发的 JWT。

## Thirdparty：第三方防腐层

`macula-samples-thirdparty` 用于隔离第三方协议与内部业务模型，目前也是运行骨架。后续可将外部 SDK、请求签名、响应转换和外部错误处理收敛在这一边界，向内部提供稳定契约。

第三方凭据由运行环境或配置中心提供；来自内部的受保护请求仍使用应用网关 JWT。不要将外部平台返回模型直接扩散到各业务服务。

## Admin：浏览器管理端

`macula-samples-admin` 基于 Vue 3、Vite、Pinia、Vue Router 与 Element Plus，独立安装和构建。业务、用户、菜单请求走同源 `/api`；登录 Token 来自外部 Macula Cloud IAM。

- 本地 Vite 默认代理到 `http://127.0.0.1:6000`，去掉 `/api` 后交给 Samples Gateway。
- IAM 地址需要能被浏览器访问；容器内部地址不能写入浏览器配置。
- Admin 根 `.env` 保存公共本地值，mode 文件覆盖差异，Vite 再读取仓库根目录的 `deploy/.env`。
- Docker 由运行时 `config.js` 提供配置；IDE 开发模式不使用该文件。

前端不是 JWT 资源服务器，不配置后端的 `jwk-set-uri`。OAuth 登记与 IAM 的 Origin 设置应与实际页面地址一致。

## 配置与源码

各模块的 application.yml 分层、地址及变量规范见本页下方“示例配置”。源码按上述模块名位于 [macula-samples 单仓项目](https://github.com/macula-projects/macula-samples/tree/main)的目录中。前端与后端共用仓库版本，构建和运行职责按模块划分。

## 示例配置

### 配置入口与职责

Samples 的后端统一使用 `src/main/resources/application.yml`，按 YAML 多文档和 profile 分层。公共约定放在公共段，本地连接值放在 `local`，容器网络差异放在 `docker`；`dev/stg/pet/prd` 保留配置中心连接信息，业务配置由 Nacos 提供。

| 配置范围 | 放置内容 |
| --- | --- |
| 公共段 | 应用名、端口占位、profile group、配置导入、路由 / 组件结构 |
| local | IDE 可用的本机地址、开发端口和本地开关 |
| docker | 容器 DNS、容器端口以及与 local 不同的值 |
| dev / stg / pet / prd | 对应环境的 Nacos 连接；其余环境值通过 Data ID 管理 |

共享的模块版本由 Parent 管理，application.yml 只承载运行配置。地址和凭据使用环境变量 / 配置中心提供的值。

### 公共段与配置导入

以下是以 Service1 为例的配置骨架；完整字段以相应模块源码为准：

```yaml
server:
  port: ${SERVER_PORT:6003}
spring:
  application:
    name: macula-samples-service1
  profiles:
    active: '@profile.active@'
    group:
      docker: local
  config:
    import:
      - optional:nacos:${spring.application.name}.yml?refreshEnabled=true
      - optional:nacos:${spring.application.name}-${spring.profiles.active}.yml?refreshEnabled=true
  cloud:
    nacos:
      server-addr: ${spring.config.nacos.server-addr}
      namespace: ${spring.config.nacos.namespace}
      username: ${spring.config.nacos.username}
      password: ${spring.config.nacos.password}
      discovery:
        namespace: ${spring.cloud.nacos.namespace}
```

`@profile.active@` 由 Maven profile 在构建时替换；`local/dev/stg/pet/prd` 定义在 Samples Parent。运行时可通过 `SPRING_PROFILES_ACTIVE` 选择环境，完整容器使用 `docker`，并通过 profile group 叠加 `local`。

`spring.config.nacos.*` 是本项目供占位引用使用的配置名；`spring.cloud.nacos.*` 是传给 Nacos 组件的属性。应用名要与 Nacos Data ID、服务发现和 Feign 目标一致。

### local 与 docker

```yaml
---
spring:
  config:
    activate:
      on-profile: local
    nacos:
      server-addr: 127.0.0.1:${NACOS_SERVER_PORT:28848}
      namespace: ${NACOS_NAMESPACE:MACULA5}
      username: ${NACOS_USERNAME:nacos}
      password: ${NACOS_PASSWORD:nacos}
  security:
    oauth2:
      resourceserver:
        jwt:
          jwk-set-uri: http://127.0.0.1:6000/oauth2/jwks
---
spring:
  config:
    activate:
      on-profile: docker
    nacos:
      server-addr: ${NACOS_SERVER_ADDR:nacos:8848}
  security:
    oauth2:
      resourceserver:
        jwt:
          jwk-set-uri: http://macula-samples-gateway:6000/oauth2/jwks
```

docker 复用 local，只覆盖有差异的值。数据库和 Redis 同理：IDE 使用宿主机发布端口，容器使用 Compose 服务名及容器端口。共享环境在对应 profile 中提供 Nacos 连接，维护 `${spring.application.name}.yml` 和 `${spring.application.name}-${spring.profiles.active}.yml` 两层配置。

### 三类地址分别配置

| 使用方 | 配置键 | 应指向 |
| --- | --- | --- |
| Gateway | `spring.security.oauth2.resourceserver.opaquetoken.introspection-uri` | Macula Cloud IAM，默认示例 `/oauth2/introspect` |
| Admin BFF | `macula.cloud.endpoint` | Macula Cloud Gateway 基础地址，System 客户端追加 `/system` |
| 所有非网关后端运行模块 | `spring.security.oauth2.resourceserver.jwt.jwk-set-uri` | **Samples Gateway** 的 `/oauth2/jwks` |

Gateway 配套设置 introspection Client；BFF 配套设置 `macula.cloud.app-key`、`secret-key`。BFF、Service1、Basic、OpenAPI、Thirdparty 都要使用应用网关的 JWK；Parent、API 契约和前端不承载该资源服务器配置。

BFF 当前使用的环境变量形式为：

```yaml
macula:
  cloud:
    endpoint: ${MACULA_CLOUD_GATEWAY_INTERNAL_URL:http://127.0.0.1:9000}
    app-key: ${MACULA_CLOUD_APP_KEY:${spring.application.name}}
    secret-key: ${MACULA_CLOUD_APP_SECRET:example}
```

这里的默认值供本地示例使用。实际部署应注入平台登记信息。内部 JVM 使用可达的内网地址；浏览器使用可公开访问的 IAM 地址，这两者由不同使用方解析。

### Redis 与持久化

- Service1 等普通业务服务使用 `spring.data.redis.*`。
- Samples Gateway 的自定义 `RedisConfiguration` 使用 `spring.redis.*` 与 `spring.redis.system.*`，分别连接项目 Redis、Cloud System Redis；遵循它的绑定代码，不做统一前缀替换。
- 数据库连接使用 `spring.datasource.*`；Service1 的 SQL 迁移放在 `db/migration/`，由 Flyway 管理。

修改数据库时追加下一版本迁移，保留已执行迁移的内容与校验信息。部署和数据持久化步骤见[打包部署](/docs/latest/04_devmanual/打包部署/)。

### .env 与前端配置的边界

`deploy/.env` 由部署脚本、Compose 和 Vite 读取，Java / Maven / IDE 不会自动读取。IDE 中要覆盖默认值时，在运行配置中设置对应环境变量。

Admin 的 `.env` 保存公共默认值，`.env.<mode>` 覆盖模式差异；当前 Vite 合并顺序为模块本地配置、仓库根目录的 `deploy/.env`、进程环境变量，后者覆盖前者。业务请求使用同源 `/api`，IAM 登录地址供浏览器直连。

后端的 `*_INTERNAL_URL` 不应直接作为浏览器地址。进入前端的 OAuth / demo 配置对浏览器可见，不用它保存服务端凭据。

### 日志与可观测性

可运行后端使用 Observability Starter。日志结构、采样率和 OTLP Metrics / Traces / Logs 的开关、endpoint 放在相应环境配置中；当前本地默认关闭网络导出。API 聚合、Parent 与 Admin 不引入该运行时配置。

源码参考：Samples 各模块的 `application.yml`、Gateway 的 `RedisConfiguration`、Parent 的 `pom.xml` 及 Admin 的 `vite.config.js`。本页记录各文件对应提交。

应用与 OAuth Client 的实际登记字段、三个连接方向及认证验收见[首次接入 Macula Cloud](/docs/latest/04_devmanual/首次接入macula-cloud/)。
