本章约束服务划分、通信、稳定性与发布。服务数量取决于业务边界和团队交付方式，不以“拆得越细”作为目标。模块职责的原理见[请求链路](/docs/latest/00_introduce/请求链路/)，实际 Samples 操作见开发指引。

## 边界与命名

服务按业务能力和数据所有权划分。能够独立解释其业务职责、数据与发布影响后，再拆成独立服务；避免仅按数据库表或前端页面拆分。

| 模块 | 约束 |
| --- | --- |
| `*-gateway` | 入口路由、认证授权、接口保护，不承载核心业务事务 |
| `*-bff` | 面向相应前端聚合接口，不作为其他业务服务的基础领域能力 |
| `*-service` 或领域服务 | 维护业务规则、状态和所属数据 |
| `*-api` | 对外调用契约，不依赖服务实现，不单独部署 |
| `*-basic` | 按需组织公共业务能力，避免成为任意逻辑的收纳箱 |
| `*-openapi` | 对外 API 适配、兼容与访问限制 |
| `*-thirdparty` | 第三方协议、错误与模型转换 |

应用名、服务发现名、Feign 目标、网关路由和 Nacos Data ID 必须能对应。Parent、API 与前端的构建方式区别于可运行后端，不为统一名称而错误启动它们。

## 通信与契约

同步调用使用受管 Feign/HTTP 客户端，显式配置连接、读取与整体业务等待预算。一次入口请求的下游超时、重试和并发应纳入同一预算，不能逐层无限叠加。

写操作重试前确认幂等语义，区分调用超时与业务失败；超时并不证明对方未提交。接口演进验证新旧调用方与服务端组合，避免共享 API 制品更新后要求所有服务同时重启才能工作。

禁止直接跨服务访问对方业务表、共享 Mapper 或绕过公开契约调用实现类。需要多个服务的数据时，选择聚合接口、事件投影或按业务设计的数据同步，不把数据库连接串作为服务集成协议。

## 数据与一致性

本地事务只保护所属数据库中的操作。跨服务状态变更先明确业务不变量、成功判定、重试、补偿与人工处置，再选择事件、可靠消息或 Seata 等机制；不为所有远程调用默认开启分布式事务。

缓存、消息和数据库的提交时机必须明确。使用 [Sender](/docs/latest/01_services/框架扩展/sender/) 时，业务记录和待发送消息应处于同一本地事务，补偿任务另行安排；消费端仍需幂等。

## 身份与权限

应用 Gateway 验证外部 Token 或应用凭据并传递内部 JWT。BFF/Service 验证应用网关的 JWT，再按方法、操作和数据归属授权；`SecurityUtils` 只读取上下文，不会自动过滤查询。

IAM 内省地址、Cloud Gateway endpoint 和应用 Gateway JWK 地址是三个方向。AK/SK、API Key 表示应用身份时，不假定其具有登录用户角色。内部网络不能替代服务端验签和数据权限，详细约束见[请求链路](/docs/latest/00_introduce/请求链路/)。

## 故障与资源隔离

- 必须为线程池、连接池、批量请求和队列设置容量边界，监控饱和及拒绝情况。
- 降级结果应有明确业务含义，不能将支付失败等同于成功，也不能无限等待依赖恢复。
- Redis、本地缓存和外部服务故障分别制定策略。Cache 的 fail-open 行为不意味着所有业务 Redis 操作都可忽略错误。
- 对第三方调用设置超时与并发限制，适配层记录可追踪的外部请求标识，不把供应商异常结构直接暴露为本方契约。

## 可观测与发布

运行服务按需接入指标、链路和日志，使用一致的服务名、环境及请求关联信息；不得把用户 ID、订单号等高基数值直接作为常规指标标签。

发布前验证就绪、健康、依赖故障和优雅停机；停止接收新请求后，为在途请求与消息处理留出退出时间。灰度标签负责路由选择，不能作为身份或租户隔离；当前负载均衡在无匹配候选时可能回退，规则见 [Alibaba](/docs/latest/01_services/微服务/alibaba/)。

数据库与消息契约采用兼容演进。先提供新能力，再迁移调用方，最后删除旧字段或接口；回滚应用并不自动回滚数据库、已发消息或已发布配置。

## 检查与相关指引

评审时确认服务边界、数据所有权、超时预算、幂等、补偿、权限、观测与回滚路径。具体运行和部署流程见[运行与测试](/docs/latest/04_devmanual/运行与测试/)、[打包部署](/docs/latest/04_devmanual/打包部署/)，组件参数见平台能力。
