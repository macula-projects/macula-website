本章以 MySQL 业务库为主要示例，约束建模、SQL、事务及版本迁移。数据库结构是长期契约，设计时同时考虑数据含义、查询方式、并发约束与演进成本；不把示例库的初始化脚本直接当作生产变更方案。

## 建模与命名

- 表和列采用统一的小写下划线命名，避免保留字，名称体现业务语义；实体与字段映射明确，不依赖含糊的隐式转换。
- 每张业务表明确主键和业务唯一性。主键使用数据库生成、TinyID 或其他方案由项目选择，必须与 Java 类型、范围和生成方式一致，不能重复生成。
- 金额使用明确精度的 DECIMAL 或经过统一约定的最小货币单位整数；不使用 FLOAT/DOUBLE 表示精确金额。
- 字符使用适当的 utf8mb4 字符集与排序规则；业务编码是否区分大小写需与唯一性约束一致。
- 空值、默认值、枚举和时间语义均要明确。未知值不得随意填成空串、0 或当前时间，以免掩盖实际数据缺失。
- 审计字段与组件映射一致。租户、逻辑删除和版本字段按业务需要设计，不为所有表机械增加相同字段。

## 建表示例

以下为新建订单表的设计示意，使用应用提供的主键和业务唯一订单号。真实字段、金额精度、时区、索引及主键策略应随需求评审。

```sql
CREATE TABLE purchase_order (
    id               BIGINT         NOT NULL COMMENT '订单ID，由应用提供',
    order_no         VARCHAR(64)    NOT NULL COMMENT '业务订单号',
    amount           DECIMAL(18, 2) NOT NULL COMMENT '金额，币种由业务另行约定',
    status           VARCHAR(32)    NOT NULL COMMENT '订单状态',
    version          INT            NOT NULL DEFAULT 0 COMMENT '并发版本',
    create_by        VARCHAR(64)    NOT NULL COMMENT '创建人',
    create_time      DATETIME(3)    NOT NULL COMMENT '创建时间',
    last_update_by   VARCHAR(64)    NOT NULL COMMENT '更新人',
    last_update_time DATETIME(3)    NOT NULL COMMENT '更新时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_order_no (order_no),
    KEY idx_status_create_time (status, create_time, id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '订单';
```

唯一索引保护并发下的业务唯一性，不能只用“先查询再插入”。多租户业务需明确订单号是否全局唯一，并据此设计组合唯一键；不直接套用本示例。

## 索引与查询

索引围绕实际过滤、关联、排序和分页设计，评估选择性、扫描行数、回表和写入成本。组合索引的列顺序结合等值、范围与排序需求验证，不按“索引越多越快”创建。

重要查询使用 EXPLAIN 等工具检查执行计划，并用接近真实的数据量评估。时间范围采用清晰边界，避免对索引列做无必要的函数或类型转换；大批量 IN、深分页和全表统计需限额或改用适合的访问方案。

应用 SQL 显式列出所需列，多表查询使用别名限定字段。MyBatis 值使用 `#{...}` 参数绑定；字段名、排序方向不能通过任意 `${...}` 接收客户端输入，应由服务端允许列表映射。

列表、导出和统计同样需要租户与数据范围。使用拦截器不能替代对自定义 SQL、忽略规则和多表关联的审查。

## 事务与并发

事务尽量短，明确隔离级别、锁顺序与回滚边界。远程调用、用户等待或大文件处理不放入长事务；死锁和锁等待超时要可观察，重试仅用于可安全重放的完整业务单元。

库存扣减、状态变更和版本更新优先利用带条件的原子 SQL，并检查影响行数。启用乐观锁不代表更新一定成功，返回 0 行时需区分不存在、版本冲突和业务条件不满足。

逻辑删除数据仍占据索引和唯一性空间，删除后的编码是否可复用要在约束设计中体现。跨服务数据通过契约或受控同步访问，不以共享数据库替代服务边界。

## 版本迁移

Macula Samples 的 Service1 使用 Flyway，迁移位于 `src/main/resources/db/migration/`。新增变更追加未使用的版本脚本，保留已经执行的脚本与校验信息；不能修改历史脚本后要求所有环境忽略校验。

| 变更 | 规约 |
| --- | --- |
| 新增可选列或索引 | 评估锁、耗时、磁盘与新旧应用兼容，先在同规模环境验证 |
| 新增强约束 | 先清理或补齐历史数据，再验证约束可建立 |
| 改名、缩短、删列或变更类型 | 采用兼容扩展、回填、切换、最后清理的分步方案 |
| 大量数据修订 | 独立分批执行，记录进度、影响行数、校验与恢复方式 |
| 基线与校验开关 | 只在明确了解库状态时使用，不能当作通用修复开关 |

现有 Samples 的 `V1__baseline.sql` 包含 `DROP TABLE IF EXISTS`，属于示例初始化资料，不能直接用于已有生产数据。共享环境的迁移需审查语句并验证空库初始化、已有库升级与重复启动；生产禁止依赖 ORM 自动改表。

## 连接、权限与发布

连接池容量按数据库预算和应用实例总数设置，不按每个实例独立放大。设置连接、查询和事务等待边界；慢查询日志需避免泄漏凭据与个人数据。

运行账号采用所需的最小权限，迁移账号可与运行账号分开管理。DDL、批量修订、备份恢复等操作应有评审、窗口及审计，业务账号不应默认拥有全库管理权限。

应用回滚不会自动撤销 DDL 和数据迁移。发布前验证新旧应用对同一结构的兼容性，并明确备份、恢复或前向修复方案，不能把重启旧镜像当作数据库恢复。

## 检查与相关资料

评审至少覆盖模型语义、主键与唯一性、索引和执行计划、查询范围、并发影响、迁移及回滚。原始原则见[阿里规范参考资料](../阿里规范/)，ORM 与 ID 接入分别见 [MyBatis-Plus](/docs/latest/01_services/框架基础/mybatisplus/)、[Data JPA](/docs/latest/01_services/框架基础/datajpa/)与 [ID 生成](/docs/latest/01_services/通用平台/id/)。
